Webhook delivery for order events

Summary

Add a delivery worker inside the existing monolith, fed by a transactional outbox table. Checkout writes the event in the same transaction as the order; the worker signs and delivers it with retries. No new service, no new datastore.

Decisions

Each key decision as a short ADR. These are what you're approving.

Use a transactional outbox, not publish-after-commit

Context
Merchants reconcile from webhooks; a lost event means a wrong ledger.
Decision
Insert the event into webhook_outbox in the order transaction. A worker delivers it.
Performance
+1 indexed insert on checkout (<2 ms p99). Worker batch of 100 every 250 ms covers 400/s per instance.
Security
Payloads signed with HMAC-SHA256, per-merchant key from KMS, timestamp in signature to block replay. Worker egress only.
Alternatives
Broker with publish-after-commit (lost events); synchronous delivery in checkout (merchant latency becomes our latency).
Consequences
Outbox table needs pruning (delivered rows deleted after 7 days). Delivery order is per-order, not global.

Open questions for you

  1. Is 24 hours of retries enough before we mark a delivery as failed and alert the merchant?
  2. Do merchants need global event ordering, or is per-order ordering enough?

Migration

Every step ships on its own and can be rolled back.

  1. Add webhook_outbox table and the signing-key lookup. No behavior change.
  2. Write outbox rows on checkout behind a flag; worker runs in dry-run mode, logging what it would send.
  3. Enable delivery for internal test merchants; compare against expectations.
  4. Enable for all merchants; add the admin view of delivery attempts.
